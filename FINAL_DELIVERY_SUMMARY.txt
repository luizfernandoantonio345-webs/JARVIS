🎓 KEY DECISIONS & RATIONALE
════════════════════════════════════════════════════════════════════════════

1. LOCAL-FIRST ARCHITECTURE
   Why: User wants offline capability with zero API costs
   Decision: Ollama local LLM as primary with cloud fallback

2. ASYNC/AWAIT THROUGHOUT
   Why: High concurrency with limited hardware
   Decision: Non-blocking I/O for all operations

3. FALLBACK CHAINS CRITICAL
   Why: Components can fail at any time
   Decision: 3-tier LLM fallback (Ollama → Claude → GPT-4o-mini)

4. TEST-DRIVEN DEPLOYMENT
   Why: Production readiness requires validation
   Decision: 40+ tests across E2E, performance, security, voice

5. COMPREHENSIVE DOCUMENTATION
   Why: Operations team needs clear procedures
   Decision: Deployment guide, runbook, API docs, ADRs

════════════════════════════════════════════════════════════════════════════
⚠️ KNOWN LIMITATIONS (Current)
════════════════════════════════════════════════════════════════════════════

1. Single-Instance Only
   Limitation: SQLite doesn't sync across multiple instances
   Workaround: Use external DB in Phase 5 (PostgreSQL)

2. No Multi-User Isolation
   Limitation: All users share same memory database
   Workaround: Add user_id field to experiences table (Phase 6)

3. Offline Required
   Limitation: Needs local Ollama for full functionality
   Workaround: Cloud API fallback partially mitigates

4. PT-BR Language Focus
   Limitation: Optimized for Portuguese (Brazil)
   Workaround: Can use other languages with TTS fallback

5. No Distributed Cache
   Limitation: Memory cache not shared across instances
   Workaround: Add Redis in Phase 5
